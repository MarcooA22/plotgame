# Contributing to PlotGame

Thanks for wanting to improve PlotGame.

Contributions can be technical or non-technical. A valuable contribution might be a gameplay feature, translation, bug fix, skin concept, UX improvement, accessibility improvement, documentation change, mathematical insight, or a strong product idea.

## Before you start

For a **non-trivial new feature or product direction**, please propose the idea before implementing it.

Preferred flow:

1. Explain the problem or opportunity.
2. Describe the expected player experience.
3. Explain why it fits PlotGame.
4. Discuss scope and trade-offs.
5. Once accepted, track it as an Issue.
6. Implement it in a Pull Request.

Until GitHub Discussions are enabled, use the feature proposal Issue template for early product ideas.

### You usually do not need prior discussion for

- obvious bug fixes
- typos
- small documentation corrections
- contained translation fixes
- small tests around existing behavior

## Pull Requests

A Pull Request should explain:

- what changed;
- why it changed;
- which Issue or proposal it relates to, when applicable;
- how it was tested;
- screenshots or a short recording for visible gameplay/UI changes;
- any mathematical or educational consequence worth reviewing.

Keep Pull Requests reasonably focused.

## AI-assisted contributions

AI-assisted development and vibe coding are welcome.

The contributor is still responsible for the contribution.

Please do not submit large amounts of generated code that you have not tested or cannot explain. Review focuses on behavior, clarity, maintainability, safety, and fit with the project, not on whether every line was typed manually.

## Translations

Translations are a first-class contribution path.

See [docs/TRANSLATIONS.md](docs/TRANSLATIONS.md).

## Community-created levels

Do not submit normal player-created levels as code Pull Requests.

The intended model is an in-game, no-code level editor and a Community Challenges section. Repository contributions should improve the editor, publishing system, validation logic, moderation, discovery, or built-in game content rather than replace the in-game publishing flow.

See [docs/COMMUNITY_LEVELS.md](docs/COMMUNITY_LEVELS.md).

## Review

Routine changes may be checked using automated tests and AI-assisted review.

AI review is advisory. Human maintainers make merge and product decisions.

Changes that affect product direction, core mathematical rules, moderation, security, or major architecture may require additional review.

## Attribution

Git history and Pull Requests should preserve who contributed what.

Do not claim another person's or an AI system's work as your own manual implementation.

## Conduct

Be constructive, specific, and respectful. Critique ideas and implementations, not people.

See [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md).
